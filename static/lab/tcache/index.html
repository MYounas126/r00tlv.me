Poison a tcache bin

Allocate two chunks, free them, and watch the tcache freelist form. Then overwrite a freed chunk's fd and see where the next malloc goes. This models glibc 2.32 and newer, so safe-linking, the tcache key and the alignment check are all in play.

The program under test

char *a = malloc(0x28);   /* 0x30-byte chunk, tcache index 1 */
char *b = malloc(0x28);
free(a);
free(b);                  /* bin head is b, LIFO */

/* a use-after-free or an overflow gives you 8 bytes of write into b */
*(size_t *)b = ((size_t)b >> 12) ^ (size_t)target;

malloc(0x28);            /* hands back b */
char *p = malloc(0x28);  /* hands back target */

Allocator controls

tcache_perthread_struct

One struct per thread, itself a heap chunk of 0x290 bytes. Only counts[1] and entries[1] matter here. Note that entries[] is stored in the clear; only the next fields inside the chunks are mangled.

What glibc actually does

/* malloc.c, trimmed */
#define PROTECT_PTR(pos, ptr) \
  ((__typeof (ptr)) ((((size_t) pos) >> 12) ^ ((size_t) ptr)))
#define REVEAL_PTR(ptr)  PROTECT_PTR (&ptr, ptr)

static tcache_put (mchunkptr chunk, size_t tc_idx)
{
  tcache_entry *e = chunk2mem (chunk);
  e->key  = tcache_key;                       /* 2.34+; before that, the tcache pointer */
  e->next = PROTECT_PTR (&e->next, tcache->entries[tc_idx]);
  tcache->entries[tc_idx] = e;                /* the head is NOT mangled */
  ++(tcache->counts[tc_idx]);
}

static void *tcache_get (size_t tc_idx)
{
  tcache_entry *e = tcache->entries[tc_idx];
  if (__glibc_unlikely (!aligned_OK (e)))        /* added in 2.32 */
    malloc_printerr ("malloc(): unaligned tcache chunk detected");
  tcache->entries[tc_idx] = REVEAL_PTR (e->next);
  --(tcache->counts[tc_idx]);
  e->key = NULL;                              /* why realloc-then-free is not a double free */
  return (void *) e;                         /* no size check at all */
}

The fast path in __libc_malloc only calls tcache_get when counts[tc_idx] > 0, which is the whole reason the classic recipe frees two chunks rather than one.

Why the old write-ups no longer work

Most tcache poisoning tutorials were written between 2018 and 2020, when a tcache bin was a plain singly linked list and the fd field held the next pointer in the clear. The move in those tutorials is one line: overwrite the fd of a freed chunk with the address you want, call malloc twice, take delivery. On anything built against glibc 2.32 or later that line stores a value which is read back through an XOR, so the pointer the allocator follows is your target combined with a key you have not accounted for.

The key is the address of the fd field itself shifted right by twelve. Twelve is the page shift, so the key is the virtual page number of the heap page the chunk sits on, and every chunk on that page shares it. Recovering it is not hard, but it is now a prerequisite. The route this lab shows is the usual one: a chunk freed into an empty bin stores (address >> 12) ^ 0, which is the key sitting in memory in plain view. Any read primitive that reaches the first eight bytes of a freed chunk gives you the key for that page, and from there you can mangle anything you like.

The second thing those tutorials skip is alignment. Since 2.32, tcache_get refuses to return a pointer that is not a multiple of sixteen, which rules out the old habit of aiming at a saved return address or at a GOT slot that happens to sit eight bytes off alignment. The work-around is to aim at the aligned address below the target and reconstruct the eight bytes you overshoot, which is why current write-ups talk about targeting target - 8.

Taken together the two changes do not close the technique, they raise its price. A blind fd overwrite that used to be a quiet win now aborts the process on the next malloc, and a working exploit needs a heap address leak plus a target you can reach from a sixteen byte boundary. That is a reasonable result for a mitigation that costs one shift and one XOR.

Version history

2.26
tcache introduced. Seven chunks per bin, 64 bins, and no integrity checking on the list whatsoever.
2.29
tcache_entry gains a key field and free starts reporting free(): double free detected in tcache 2.
2.30
counts[] widened from char to uint16_t, which is why the perthread struct chunk grew from 0x250 to 0x290 bytes.
2.32
Safe-linking applied to tcache and fastbin fd pointers, and tcache_get gains the aligned_OK check.
2.34
tcache_key becomes a random value from getrandom rather than the address of the perthread struct. The malloc hooks were removed in the same release, which retired __free_hook as a target.

Assumptions and simplifications

  • The addresses are plausible rather than real. The heap base is fixed at 0x555555559000, which is what a PIE binary with ASLR disabled tends to show, and nothing here varies between runs.
  • Memory outside the chunks this model knows about reads back as zero. On a real target it holds whatever was there, which matters because the second malloc reads eight bytes from your target address and writes eight bytes of zero at target + 8 when it clears the key.
  • Only one bin is modelled, index 1, for 0x30-byte chunks. A real tcache has 64 bins and a thread has one perthread struct for all of them.
  • The checks free performs before it reaches the tcache path, such as free(): invalid pointer and free(): invalid size, are not modelled.
  • The bin cannot fill up here, so the fall-through from a full tcache into the fastbin and the unsorted bin is out of scope.
  • The double-free scan is modelled with the three checks current glibc performs in that loop, in source order. The release that added each individual check inside the loop is not asserted on this page, only the release that added the loop.
  • The key check is a heuristic in real glibc too. A chunk whose key field happens to match by coincidence triggers the scan, and free carries on normally when the chunk is not found in the bin.
