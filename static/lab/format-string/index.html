Where each argument comes from

The part most write-ups get wrong. On 32-bit x86 every variadic argument is pushed onto the stack, so the first %x in a hostile format string reads the first stack word straight away. The System V AMD64 convention does not work like that. Integer and pointer arguments travel in RDI, RSI, RDX, RCX, R8 and R9, and only the seventh onwards is placed in memory. printf spends RDI on the format string itself, so variadic arguments one to five live in RSI, RDX, RCX, R8 and R9, and argument six is the first one that comes off the stack. That is why %p %p %p %p leaks four registers here and touches no stack at all, and why %6$p is the first offset worth typing on this target.

Why the register detail matters

printf is itself a variadic function, so its prologue spills RSI through R9 into a register save area on its own frame, and the va_list walks that area before it ever looks at the caller. When the caller passed no variadic arguments at all, those five registers still hold whatever the preceding code left in them. The first five conversions therefore leak register residue, which is usually a pointer into libc or a loop counter, and only from the sixth does gp_offset reach 48 and the va_list switch over to overflow_arg_area, which points into the caller's frame.

The call site also sets AL to zero, because no vector registers are in use. That tells printf to skip the XMM half of the save area entirely, so a %f in a hostile format string reads a region that was never filled in. The walk above marks floating point conversions as out of scope rather than guessing at them.

The practical consequence for anyone hunting an offset is that the numbers quoted in older write-ups are five too low on this target. The usual approach still works: put a recognisable marker at the front of the string, then probe %6$p, %7$p and upwards until the marker appears back in the output. Once you can see your own bytes in a leaked slot you control both the value and the pointer, and %n turns that into a write of your choosing.

Modern toolchains do push back. GCC and Clang emit -Wformat-security, most distributions build with -Werror=format-security, and _FORTIFY_SOURCE rejects %n when the format string sits in writable memory. Android's bionic dropped %n altogether. None of that helps code built without the flags, which is most firmware.

What this model does not do

  • Addresses, register residue and slot contents are plausible stand-ins rather than a capture from a running process. There is no ASLR, and the frame is laid out for a System V AMD64 target with the frame pointer kept.
  • Only a handful of addresses have known contents. Anything inside the modelled stack, libc or image ranges counts as readable, and where the bytes are not modelled the output shows a placeholder rather than inventing them.
  • Register residue is not predictable in a real program. What the preceding library call leaves in RSI through R9 depends on the libc build, the input and the optimisation level.
  • %n is shown as a write, but the written bytes are not fed back into the model. A real printf parses the format as it goes, so a write landing inside buf would change the rest of the walk.
  • Floating point conversions take their argument from the SSE save area, not from the integer registers or the stack, so they are listed and skipped.
  • Width and precision are handled for the common cases. The ' grouping flag, %a, and locale effects are not modelled.
  • The four padding bytes above the int n at rbp-0x30 are shown as zero. A real frame holds whatever was there before.
  • The byte counter that %n reports uses UTF-8 byte length, which is what printf would count. Characters outside the Basic Multilingual Plane are not encoded correctly by the counter.
  • Field widths and precisions above 512 are clamped by this page so the output pane stays readable. A real printf honours them, which is how a single %n is made to store a large value.
  • Output appears here as soon as it is produced. A real printf writing to a terminal is line buffered, so a crash partway through usually loses everything written since the last newline.
